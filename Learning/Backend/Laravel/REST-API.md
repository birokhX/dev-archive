این ساختار، نقطه شروع است و نه قانونی که باید برای هر پروژه عیناً اجرا شود.

- Controller: درخواست HTTP را دریافت می‌کند، سرویس مناسب را فراخوانی می‌کند و پاسخ HTTP را برمی‌گرداند.
    
- Form Request: داده ورودی را اعتبارسنجی می‌کند و در صورت نیاز مجوز همان عملیات را بررسی می‌کند.
    
- Resource: تعیین می‌کند چه داده‌ای در خروجی JSON نمایش داده شود.
	
- Service: منطق کسب‌وکار را پیاده می‌کند؛ به‌ویژه وقتی عملیات چند مرحله دارد یا در چند جای برنامه استفاده می‌شود.
    
- Policy: بررسی می‌کند کاربر اجازه انجام عملیات روی یک رکورد مشخص را دارد یا خیر.
    
- Feature Test: درخواست واقعی HTTP را آزمایش می‌کند، نه فقط یک متد PHP را.

**نکته حرفه‌ای:** **Service**، **Repository** و **DTO** الزام همیشگی **Laravel** نیستند. از **Service** در بخش‌هایی استفاده می‌کنیم که منطق کسب‌وکار ارزش جدا شدن دارد. **Repository** را فقط زمانی اضافه می‌کنیم که مسئله واقعی در دسترسی به داده‌ها، چند پیاده‌سازی یا پیچیدگی کوئری‌ها داشته باشیم. این رویکرد از معماری بیش‌ازحد پیچیده جلوگیری می‌کند.

#### مفهوم `V1` در ساختار REST API
`V1` مخفف **Version 1** (نسخه ۱) هست و به مفهوم **API Versioning** (نسخه‌بندی API) اشاره داره. این یکی از مهم‌ترین مفاهیم در طراحی APIهای حرفه‌ای و قابل نگهداری هست.
##### چرا نسخه‌بندی API لازمه؟

فرض کن API شما الان در اپ موبایل و وب‌سایت‌ها استفاده می‌شه. حالا می‌خوای یک فیلد رو از پاسخ حذف کنی یا ساختار پاسخ رو تغییر بدی. اگه این کار رو بدون نسخه‌بندی انجام بدی:

- اپ‌های قدیمی که هنوز آپدیت نشدن **خراب می‌شن**.
    
- کلاینت‌های مختلفی که به API وصلن قطع می‌شن.

##### نتیجه در URL
نسخه‌بندی معمولاً در مسیر URL ظاهر می‌شه:
با نسخه‌بندی، می‌تونی نسخه قدیمی (`V1`) رو **فعال نگه داری** تا کلاینت‌ها مهاجرت کنن، و همزمان نسخه جدید (`V2`) رو با تغییرات اعمال‌شده ارائه بدی.

```php
GET  /api/v1/contacts      → نسخه ۱
POST /api/v1/contacts
GET  /api/v2/contacts      → نسخه ۲ (با ساختار جدید)
```

به همین دلیل در پروژه شما این مسیرها وجود داره:
```php
Controllers/Api/V1/User/ContactController.php
Requests/Api/V1/User/Contact/...
Resources/Api/V1/User/ContactResource.php
```

```php
Route::prefix('v1')->group(function () {
    Route::apiResource('contacts', V1\User\ContactController::class);
});
Route::prefix('v2')->group(function () {
    Route::apiResource('contacts', V2\User\ContactController::class);
});
```


### جلسه اول: طراحی REST endpointها

قبل از نوشتن Controller باید قرارداد API را مشخص کنیم. در پروژه‌های حرفه‌ای، ابتدا تصمیم می‌گیریم مصرف‌کننده چه درخواستی می‌فرستد و چه پاسخی می‌گیرد؛ سپس پیاده‌سازی می‌کنیم.
فرض کن مخاطبین به یک کسب‌وکار تعلق دارند و کاربر فقط اجازه مدیریت مخاطبین کسب‌وکار خودش را دارد.

### قرارداد اولیه

|عملیات|متد HTTP|Endpoint|
|---|---|---|
|نمایش فهرست مخاطبین|`GET`|`/api/v1/user/contacts`|
|نمایش یک مخاطب|`GET`|`/api/v1/user/contacts/{contact}`|
|ساخت مخاطب|`POST`|`/api/v1/user/contacts`|
|ویرایش کامل مخاطب|`PUT`|`/api/v1/user/contacts/{contact}`|
|ویرایش بخشی از مخاطب|`PATCH`|`/api/v1/user/contacts/{contact}`|
|حذف مخاطب|`DELETE`|`/api/v1/user/contacts/{contact}`|
این مسیرها قرارداد پیشنهادی پروژه آموزشی ما هستند، نه تنها شکل معتبر طراحی REST.
چرا `contacts` جمع است؟ چون این endpoint به مجموعه‌ای از منابع مخاطب اشاره می‌کند. چرا برای ایجاد مخاطب از `POST` استفاده می‌کنیم؟ چون قرار است یک منبع جدید در مجموعه ساخته شود.

یک تفاوت مهم دیگر:
- `PUT` معمولاً برای جایگزینی کامل نمایش یک منبع به کار می‌رود.
    
- `PATCH` برای تغییر بخشی از منبع است.
    
- `DELETE` برای حذف منبع است.
    
- `GET` نباید باعث تغییر وضعیت کسب‌وکار شود.

اگر فقط نام مخاطب را تغییر می‌دهیم، `PATCH` معمولاً انتخاب مناسب‌تری است. اگر `PUT` را هم پشتیبانی کنیم، باید معنای آن را دقیق تعریف کنیم و اعتبارسنجی‌اش با همان معنا هماهنگ باشد.

**نکته:** ما در پروژه آموزشی از `JsonResource` استفاده می‌کنیم تا ساختار خروجی را کنترل کنیم و ناخواسته فیلدهای حساس یا داخلی مدل را به مصرف‌کننده تحویل ندهیم. مستندات رسمی Laravel هم Resource را برای همین لایه تبدیل مدل به JSON معرفی می‌کند.

### اولین پیاده‌سازی در Laravel 13
ابتدا اگر پروژه‌ات API routing را فعال نکرده است، در ریشه پروژه اجرا کن:
```bash
php artisan install:api
```

در Laravel 13 این دستور فایل `routes/api.php` را ایجاد می‌کند و Sanctum را برای احراز هویت API نصب می‌کند. اگر API و Sanctum از قبل نصب شده‌اند، دوباره این مرحله لازم نیست.

<br>

سپس برای ایجاد فایل‌های اصلی:

```Bash
php artisan make:controller Api/V1/User/ContactController --api

php artisan make:request Api/V1/User/Contact/StoreContactRequest

php artisan make:request Api/V1/User/Contact/UpdateContactRequest

php artisan make:resource Api/V1/User/ContactResource
```
نام‌گذاری مسیرها و namespaceها باید با ساختار واقعی پروژه هماهنگ باشد؛ این دستورات نقطه شروع پیاده‌سازی هستند.

<br>

در `routes/api.php`:

```php
<?php
use App\Http\Controllers\Api\V1\User\ContactController;
use Illuminate\Support\Facades\Route;

Route::prefix('v1/user')
    ->name('api.v1.user.')
    ->group(function () {
        Route::apiResource('contacts', ContactController::class);
    });
```

با این تعریف، Laravel endpointهای متداول CRUD را ثبت می‌کند. چون فایل `api.php` به‌صورت پیش‌فرض prefix مربوط به API را دریافت می‌کند، نیازی نیست `/api` را دوباره به مسیرها اضافه کنی.

برای دیدن مسیرهای ثبت‌شده:

```Bash
php artisan route:list --path=api
```

توجه: این مرحله فقط مسیرها را ثبت می‌کند. هنوز احراز هویت، مجوز دسترسی، اعتبارسنجی، Resource و منطق Controller را پیاده نکرده‌ایم. تا پیش از اضافه شدن این لایه‌ها، endpointهای نوشتن و حذف را به‌عنوان API آماده انتشار در نظر نگیر.

### از همین ابتدا چه اشتباهاتی را باید کنار بگذاری؟

**اشتباه اول: برگرداندن مستقیم تمام مدل**
مثلاً `return Contact::all();` در همه endpointها. این کار کنترل خروجی را محدود می‌کند و با رشد مدل ممکن است فیلدهای ناخواسته منتشر شوند. از Resource و انتخاب صریح فیلدها استفاده کن.

**اشتباه دوم: اعتماد به ID ارسالی کاربر**
حتی اگر کاربر وارد شده باشد، ممکن است ID مخاطب فرد دیگری را ارسال کند. کوئری‌ها و Policy باید مالکیت و مجوز دسترسی را تضمین کنند.

**اشتباه سوم: اعتبارسنجی فقط در فرانت‌اند**
هر مصرف‌کننده می‌تواند درخواست HTTP را مستقیم ارسال کند. اعتبارسنجی اصلی باید در سمت سرور انجام شود و داده ورودی از `validated()` گرفته شود.

**اشتباه چهارم: ساختن یک ساختار پیچیده برای هر CRUD ساده**
Service، Repository، DTO و کلاس‌های عمومی متعدد لزوماً کیفیت را بالا نمی‌برند. هر لایه باید مسئولیت مشخص و دلیل وجودی داشته باشد.

#### احراز هویت را از همین ابتدا درست انتخاب کن

برای استفاده از API در اپلیکیشن موبایل یا مصرف‌کنندگان مستقل، Sanctum می‌تواند توکن‌های API صادر و لغو کند. برای یک SPA متعلق به خودت، Sanctum از احراز هویت مبتنی بر session و cookie هم پشتیبانی می‌کند؛ این دو روش را نباید با یکدیگر اشتباه بگیری.

همچنین، `auth:sanctum` فقط احراز هویت است؛ به‌تنهایی ثابت نمی‌کند کاربر مالک یک مخاطب است. این بررسی را در مرحله Authorization با Policy و کوئری‌های محدود به مالک انجام خواهیم داد.
